# DeepSeek Agent — День 22

Локальный веб-чат с отдельной сущностью агента, несколькими диалогами, пресетами и автоматическим сохранением контекста в JSON.

## Первый RAG-запрос — День 22

В строке настроек чата появился переключатель **RAG**. Для каждого сообщения
можно выбрать `Structural`, `Fixed` или `Combined` и `top-K` от 1 до 20.
Выключенный переключатель оставляет прежний поток запроса без документального
контекста. Включённый выполняет локальный поиск, удаляет точные дубликаты
чанков и добавляет найденные фрагменты в системный контекст DeepSeek.

В **«Управлении RAG»** находится независимая лаборатория сравнения. Она делает
два последовательных вызова DeepSeek с одинаковым вопросом, настройками и
историей: первый без документов, второй с RAG. Эти ответы не попадают в
обычный диалог и сохраняются в `data/rag_evaluations.json`. Контрольный набор
из 10 вопросов находится в `docs/day22_control_questions.json`.

Порог релевантности, реранкер и query rewrite намеренно не входят в этот этап:
они относятся к Дню 23. Обязательные цитаты и режим «не знаю» относятся к Дню 24.

## Локальная индексация документов — День 21

Переключатель **«Чат / Управление RAG»** открывает отдельный локальный конвейер
индексации. Положите PDF с текстовым слоем, DOCX, TXT, Markdown или HTML/HTM в
`rag_documents/`, обновите список и нажмите **«Построить оба индекса»**.

Приложение одновременно строит fixed-чанки и structural-чанки, вычисляет на CPU
нормализованные эмбеддинги `intfloat/multilingual-e5-small` и сохраняет текст,
векторы и метаданные в `data/rag_index.sqlite3`. В интерфейсе доступны статистика,
постраничный просмотр чанков и одинаковый семантический поиск `top-K` по обеим
стратегиям. Сам семантический поиск локален; DeepSeek вызывается только обычным
чатом при включённом RAG или отдельной кнопкой сравнения Дня 22.

DOCX обрабатывается по заголовкам, абзацам, спискам и таблицам; изображения и
текст внутри них не распознаются. HTML обрабатывается без исполнения JavaScript. PDF без текстового слоя получает
понятную ошибку; OCR и загрузка страниц по URL в День 21 не входят.

## Общий выключатель MCP

В верхней части правой панели находится карточка **«Все MCP»**. Кнопка
**«Отключить все MCP»** немедленно сохраняет общую блокировку, останавливает
Filesystem, Open‑Meteo, Scheduler, MediaWiki и World Bank MCP и не передаёт их
инструменты модели. Пока блокировка активна, запрещены ручной, ленивый и
автоматический запуск MCP, в том числе после перезапуска приложения.

**«Разрешить MCP»** снимает только блокировку. Серверы при этом остаются
остановленными и могут быть запущены отдельно штатными кнопками или при следующем
обычном старте приложения.

## Оркестрация нескольких MCP-серверов — День 20

В проект установлены готовые `@professional-wiki/mediawiki-mcp-server` и
`@cyanheads/worldbank-mcp-server`. При обычном запуске приложения оба
подключаются как независимые долгоживущие процессы по `stdio` без API-ключей.
DeepSeek одновременно получает безопасный read-only набор MediaWiki, девять
инструментов World Bank и инструменты уже запущенных локальных MCP-серверов.

Агент сам выбирает сервер и может строить зависимую цепочку: сначала найти
страны или объекты через Wikipedia, затем использовать фактически найденные
коды в запросе World Bank. В правой панели у каждого сервера есть отдельные
состояние, запуск, полный `tools/list` и остановка. По умолчанию используется
русская Wikipedia в принудительном read-only режиме. MediaWiki сообщает полный
набор сервера, но модели передаются только поиск и чтение страниц.

Во время ожидания ответа под сообщением показывается живой список MCP-вызовов:
сервер, инструмент, безопасные аргументы и состояние. После ответа порядок
остаётся в отдельном блоке сообщения и в техническом `mcp_tool_calls`.

## Композиция MCP-инструментов — День 19

Один запрос может автоматически собрать погодный отчёт из нескольких шагов.
Например: «Узнай погоду в Новосибирске, посоветуй одежду и сохрани отчёт в
файл». DeepSeek вызывает инструменты Open‑Meteo, получает исходные данные,
самостоятельно обрабатывает их согласно формулировке пользователя, а затем
вызывает `write_file` официального Filesystem MCP.

Filesystem MCP запускается лениво только для сообщения с явной просьбой
сохранить, записать, выгрузить или создать файл/документ/отчёт. Обычный вопрос
о погоде не запускает файловый сервер и не предоставляет модели `write_file`.
Модель никогда не получает остальные файловые инструменты. Приложение заменяет
предложенный моделью каталог на `workspace/reports`, очищает базовое имя,
принудительно использует Markdown и добавляет новосибирские дату и время:
`weather-2026-09-27-18-30-00.md`. Поэтому существующий отчёт не
перезаписывается, а попытка указать путь за пределами workspace игнорируется.

Порядок и аргументы вызовов сохраняются в `mcp_tool_calls`. Для типичного
запроса по названию города цепочка выглядит как `find_location` →
`get_daily_forecast` → обработка DeepSeek → `write_file`. Если запись или
обязательная проверка ответа завершается ошибкой, созданный этим запросом файл
компенсирующе удаляется.

## Планировщик и фоновые задачи — День 18

Кнопка **«Расписание»** открывает локальный Scheduler. Он поддерживает разовый
запуск по новосибирскому времени, запуск «через N минут» и период с минимальным
интервалом 5 минут. Задания, история запусков, ошибки и непрочитанные результаты
хранятся в `data/scheduler.sqlite3`. Диалоги автоматизаций остаются в обычном
JSON-хранилище.

Scheduler MCP автоматически подключается при обычном запуске приложения.
Поэтому можно написать в чате: «Через час узнай погоду в Новосибирске и
посоветуй одежду». Агент вызывает `create_scheduled_task`, сохраняет будущий
промпт и точный allowlist зависимостей Open‑Meteo. В назначенное время Scheduler
запускает отсутствующий погодный MCP, выполняет запрос через DeepSeek и помещает
ответ в отдельный диалог `Автоматизация · ...`.

В окне расписания доступны создание, изменение, пауза, продолжение, немедленный
запуск, переход в диалог и удаление расписания. История показывает результаты и
ошибки, а счётчик у кнопки — непрочитанные завершения. Инструмент
`get_scheduler_summary` возвращает агрегаты по заданиям и запускам.

Scheduler работает только вместе с Flask-приложением. После простоя разовые
задания помечаются как пропущенные, а периодические продолжаются с ближайшего
будущего интервала; пропущенные запросы к DeepSeek не догоняются. Автоматические
запуски расходуют токены DeepSeek. Системные уведомления Windows и автозапуск
приложения не используются.

## Первый собственный MCP-инструмент — День 17

В `mcp_servers/` находятся три независимых MCP-сервера на Python:

- **Open‑Meteo MCP** — `find_location`, `get_current_weather`,
  `get_hourly_forecast`, `get_daily_forecast`, `get_precipitation_window`;
- **OpenAlex MCP** — поиск научных работ, карточка работы и поиск авторов;
- **OpenAQ MCP** — поиск станций, сведения о станции и последние измерения.

Open‑Meteo подключён к приложению. Запустите его отдельной карточкой в правой
панели, затем напишите: «Какая сейчас погода в Новосибирске и что надеть?».
DeepSeek сам выбирает инструменты, получает данные через MCP и формирует ответ.
В технических данных сохраняется список выполненных `mcp_tool_calls`. Это
сетевой запрос к бесплатному Open‑Meteo API и обычный оплачиваемый запрос к
DeepSeek.

OpenAlex и OpenAQ пока не передаются модели. Open‑Meteo и OpenAlex не требуют
регистрации. OpenAQ v3 требует бесплатный `OPENAQ_API_KEY` в `.env`. Подробности
отдельного запуска находятся в `mcp_servers/README.md`.

## Локальное MCP-соединение — День 16

В правой панели находится карточка **Filesystem MCP**. Кнопка **«Запустить
MCP»** поднимает официальный `@modelcontextprotocol/server-filesystem` как
локальный дочерний процесс и устанавливает с ним долгоживущее соединение по
`stdio`. **«Получить инструменты»** использует ту же сессию и показывает имя и
версию сервера, согласованную версию протокола, количество инструментов, их
описания и JSON Schema входных параметров. **«Остановить MCP»** закрывает сессию
и завершает процесс. Повторный запуск второго экземпляра не выполняется.

Filesystem Server получает единственный разрешённый путь — папку `workspace`
внутри проекта. Остальные файлы проекта ему не передаются. Обычно инструменты
только демонстрируются в интерфейсе; при явной команде файлового экспорта
DeepSeek временно получает только `write_file`, а приложение дополнительно
ограничивает его новым Markdown-файлом в `workspace/reports`. При штатном
завершении Flask дочерние MCP-процессы очищаются.

## Контролируемый жизненный цикл — День 15

В начале карточки находится общий переключатель машины задач. **«Отключить
машину задач»** действует сразу на все диалоги и сохраняется после перезапуска:
чат отвечает без этапных ограничений, независимого LLM-валидатора, handoff и
автопилота. MCP, RAG и выбранная стратегия контекста продолжают работать.
Текущие этапы, планы и история переходов не удаляются; после повторного
включения каждый диалог продолжает с сохранённого состояния.

У каждого диалога есть одна карточка текущей задачи: описание, этап, текущий
шаг, ожидаемое действие, краткий план и активность. Допустимы четыре этапа:
`planning`, `execution`, `validation`, `done`. Прямое редактирование этапа
запрещено: состояние принимает только разрешённые события графа Дня 15.
Переключатель управления переходами выбирает ручные кнопки или автопилот.

Основной путь: **утвердить план → выполнить → проверить → завершить**. Из
`execution` можно вернуться в `planning`, а неуспешная валидация возвращает в
`execution`. Попытка перепрыгнуть этап отклоняется с HTTP 409 и не изменяет
сохранённый JSON. Все изменения и переходы записываются в историю карточки.

В ручном варианте пользователь нажимает одну из разрешённых кнопок. В режиме
**«Автопилот»** независимый контроллер после каждого успешного ответа определяет,
завершён ли этап, и рекомендует конкретное разрешённое событие. Сервер повторно
проверяет рекомендацию, формирует handoff, выполняет переход и принимает
служебное продолжение следующего этапа. Автопилот останавливается при блокировке,
необходимости уточнения, ошибке или после шести последовательных переходов.
Кнопка **«Остановить автопилот»** запрещает новые автоматические сообщения и
возвращает ручное управление после завершения уже начатого запроса.

Если результатом задачи должны быть файлы, контроллер фиксирует их точные пути
на этапе планирования. На `execution` модель обязана вернуть полное содержимое
каждого файла в именованном блоке артефакта; сервер сохраняет его локально,
считает размер, версию и SHA-256. Переход в `validation` блокируется, пока
обязательных файлов нет, а переход в `done` — пока текущая валидация не
подтвердила их существование и неизменность. После завершения сервер всегда
делает последний LLM-вызов уже на этапе `done`: модель получает итоговый
handoff и точный реестр файлов, после чего её ответ показывается отдельным
итоговым результатом с кнопками **«Открыть»** и **«Скачать»**.
HTML открывается в изолированном режиме без выполнения скриптов и внешних
ресурсов. Файлы лежат в `data/artifacts/` и не попадают в Git.
Для нефайловой задачи список обязательных артефактов остаётся пустым: файловые
проверки не применяются, а финальный LLM-ответ всё равно формируется по handoff
завершённой валидации. Если последний вызов или его контроль не удался, переход
в `done` не сохраняется и его можно безопасно повторить.

Кнопка **«Приостановить»** сохраняет этап и все поля, после чего сервер блокирует
новые действия агента в этом диалоге. **«Продолжить»** возвращает возможность
работы с того же шага без повторного объяснения. Актуальное состояние добавляется
в системный контекст каждого запроса, а его неизменяемый снимок сохраняется в
технических данных пользовательского сообщения и ответа.
Сохранённый этап считается авторитетным: агент не должен вычислять его заново
по содержанию прежней переписки, summary или facts. Кнопка **«Показать
состояние»** и локальная команда `/state` читают данные прямо с сервера, не
обращаясь к DeepSeek и не расходуя токены.

Этап теперь управляет не только подписью, но и допустимым поведением. Основная
модель получает этап и инварианты, но возвращает обычный пользовательский текст
без служебного JSON. Отдельный проверяющий LLM-вызов возвращает структурированный
отчёт и классифицирует фактическое содержание черновика. Ответ с
реализацией на этапе `planning`, новая функциональность во время `validation`
или продолжение работы после `done` блокируются до сохранения в успешный
контекст. В карточке ответа показывается краткий аудит: этап, распознанное
действие и количество проверенных инвариантов. У заблокированного ответа
появляется кнопка **«Сгенерировать заново»**: она повторяет исходный запрос без
дублирования пользовательского сообщения и снова пропускает новый черновик
через контроль этапа и инвариантов. Поэтому
один пользовательский запрос обычно расходует два DeepSeek-вызова: генерацию и
проверку. Механические переходы и пауза при этом проверяются сервером без LLM.

При переходе между этапами успешная история завершаемого этапа автоматически
сворачивается в структурированный **handoff**: итог, утверждённый план, решения,
ограничения, критерии готовности, выполненная работа, результаты проверки и
открытые вопросы. Следующий этап получает handoff и только собственную новую
историю; сообщения, summary и автоматические facts прежних этапов остаются в
JSON для аудита, но больше не влияют на генерацию. Пауза не создаёт новый этап,
а ошибка формирования handoff отменяет переход без изменения состояния.

## Инварианты — День 14

Инварианты хранятся отдельно от диалогов в `data/invariants.json`. Редактируемые
наборы разделены на три слоя: профиль пользователя, проект и конкретная задача.
Можно создать несколько вариантов, временно выключать их и использовать разные
наборы в разных задачах. Read-only системная политика остаётся четвёртым,
наивысшим слоем. Для каждого запроса правила собираются в порядке:
**система → пользователь → проект → задача**.

Основная модель получает все активные правила и должна учитывать их в обычном
ответе. Проверяющая модель обязана перечислить все проверенные правила; её
структурированный отчёт не выпускает черновик, если фактическое действие нарушает
этап или инвариант. Источник истины остаётся в
отдельном файле, а у ответа сохраняется неизменяемый аудит применённых правил.

## Персонализация — День 12

В левом верхнем углу выбирается активный профиль. У каждого профиля свои язык,
уровень подготовки, подробность, тон, формат, дополнительные инструкции и
долговременная память. Профиль автоматически применяется к каждому следующему
запросу и работает одновременно с выбранным пресетом. Автор пользовательского
сообщения и снимок профиля ответа сохраняются в истории.

Новый профиль начинает с пустого списка. Диалоги без проекта видит только их
владелец. Владелец проекта может открыть доступ другим профилям кнопкой рядом с
названием проекта; участник сразу получает весь проект, его общую память, все
текущие и будущие диалоги. Личная память участников не смешивается. Старые данные
автоматически относятся к профилю **«Основной пользователь»**.

## Память ассистента — День 11

Кнопка **«Память»** открывает четыре слоя: текущий диалог, проект,
пользователь и постоянную политику. Диалоги можно объединять проектом; ручные
записи подтверждены и защищены, а автоматически извлечённые записи сразу считаются
подтверждёнными, но остаются редактируемыми и удаляемыми. Проектное
автоизвлечение включено для новых проектов и новых профилей. У мигрированного
профиля «Основной пользователь» сохраняется прежнее значение переключателя.

У каждого успешного ответа есть действие **«Какая память использована»**. Оно
открывает неизменяемый снимок правил и записей, реально включённых в запрос.
Изменение или удаление исходной записи этот снимок не меняет. Политика видима в
интерфейсе, но не имеет API редактирования. Подробная схема, API и сценарий
демонстрации описаны в `docs/MEMORY_ARCHITECTURE.md`.

Проекты и диалоги теперь сгруппированы прямо в левом сайдбаре. **«＋ Проект»**
создаёт проект с пустым диалогом, а маленький `＋` рядом с проектом — следующий
диалог внутри него. Непривязанный диалог можно перетащить в проект. Если
перетащить диалог из одного проекта в другой, в новом проекте создаётся
независимая копия, а оригинал остаётся на месте. Кнопка `↻` рядом с диалогом
явно извлекает проектную память из его успешной истории; это отдельный сетевой
вызов, поэтому он не запускается скрыто при копировании.

## Возможности

- `Agent` в отдельном файле управляет историей запроса и обращением к LLM через провайдер.
- Несколько диалогов: создание, переименование, удаление, экспорт и импорт.
- Каждый диалог автоматически записывается после сообщения и восстанавливается после перезапуска.
- Каждый диалог хранит формализованное состояние одной задачи и восстанавливает его после перезапуска.
- Пресеты содержат системный промпт и параметры DeepSeek.
- В одном диалоге можно переключать пресеты или применять разовые настройки.
- Для каждого запроса сохраняется точный снимок настроек, даже если исходный пресет позднее изменён.
- Reasoning не смешивается с ответом: `reasoning_content` хранится отдельно и показывается только в раскрываемом блоке.
- Технические данные включают время ответа, модель, request ID, fingerprint, причину завершения, входные, выходные, кэшированные, некэшированные и reasoning-токены.
- Возле каждого запроса явно показан точный размер отправленного контекста и его разбиение на кэшированные и некэшированные токены.
- Возле ответа показаны выходные, reasoning-токены, итог текущего вызова и накопленный итог на этом шаге диалога.
- В шапке отображаются суммы входных, выходных, reasoning-, кэшированных и всех токенов за диалог, а также доля последнего фактически отправленного контекста от окна выбранной модели.
- JSON записывается атомарно, чтобы прерванная запись не повредила основной файл.
- Запуск, HTTP-запросы, обращения к DeepSeek, Whisper и технические ошибки записываются в ротационные журналы.
- Режим контекста задаётся отдельно для каждого диалога: полная история, summary, Sliding Window, Sticky Facts или Branching.
- При сжатии последние 5 обменов остаются дословно, а каждые 5 более старых обменов сворачиваются.
- Все исходные сообщения, действующий summary, предыдущие версии и токены суммаризации сохраняются в JSON.
- Sliding Window отправляет только последние N обменов; N настраивается от 1 до 50.
- Sticky Facts автоматически обновляет key-value память после каждого сообщения пользователя только в этом режиме.
- Facts можно добавлять, редактировать, закреплять, откреплять и удалять вручную.
- Branching создаёт дерево от любого сообщения, сохраняет исходные пути и переключает соседние ветки через 1/N.
- Голосовой ввод работает полностью локально через `whisper.cpp`, Vulkan и RX 6600.
- Модель `large-v3-turbo` загружается при старте и остаётся в видеопамяти до закрытия приложения.

## Локальный голосовой ввод

Голосовое распознавание не использует облачный API и ничего не отправляет в интернет. Компоненты хранятся внутри проекта:

```text
models/ggml-large-v3-turbo.bin       модель Whisper
tools/whisper/bin/whisper-server.exe постоянный Vulkan-сервер
tools/ffmpeg/bin/ffmpeg.exe          переносимый конвертер аудио
```

Для первой установки дважды щёлкните `setup_voice.bat`. Скрипт:

1. проверит Vulkan SDK и Visual Studio Build Tools;
2. скачает официальный исходный код `whisper.cpp`;
3. скачает модель `large-v3-turbo` и проверит её SHA-1;
4. положит portable FFmpeg внутрь проекта;
5. соберёт `whisper-server.exe` с `GGML_VULKAN=ON`.

При обычном запуске `run.bat` Whisper стартует в фоне одновременно с чатом. Для проекта используется фиксированный локальный порт `8091`: повторный экземпляр приложения переиспользует уже работающий проектный `whisper-server`, а посторонний процесс на этом порту вызывает понятную ошибку вместо загрузки второй копии модели. PID и порт видны в статусе голоса и `GET /api/voice/status`. Служебный файл `logs/whisper-runtime.json` хранит PID сервера и подключённых экземпляров приложения; осиротевшая после принудительного завершения копия подхватывается следующим запуском.

Модель загружается один раз и остаётся в памяти RX 6600. Кнопка микрофона станет доступна после статуса **«Whisper готов»**. Повторное нажатие микрофона останавливает запись и подставляет распознанный текст в поле для проверки. Если во время записи нажать стрелку отправки, запись остановится, Whisper локально распознает аудио, а текст сразу уйдёт в DeepSeek без промежуточного редактирования.

Для остановки нажмите `Ctrl+C` в консоли приложения. Экземпляр приложения удаляется из реестра клиентов; последний клиент завершает только подтверждённый проектный `whisper-server` и освобождает видеопамять. Аудиозаписи не сохраняются на диск и не добавляются в JSON диалогов.

## Логи и диагностика

При запуске через `run.bat` автоматически создаётся папка `logs` рядом с программой:

```text
logs/app.log       общий ход работы приложения
logs/errors.log    только ошибки и их технические подробности
```

Когда файл достигает 5 МБ, он автоматически переименовывается в `app.log.1`, затем `app.log.2` и так далее. Хранятся пять предыдущих файлов каждого вида, поэтому журналы не будут бесконечно занимать диск.

В логах фиксируются запуск и остановка, выбранный порт, версии Python и Windows, HTTP-метод и путь, код ответа, время выполнения, идентификатор диалога, модель, длительность и токены DeepSeek, состояния Whisper, а также ошибки чтения и записи JSON. Тексты сообщений, ответы модели, системные промпты и аудиозаписи специально не записываются. API-ключ дополнительно маскируется, если случайно встретится в сообщении об ошибке.

Чтобы передать проблему для разбора:

1. Запустите приложение и повторите ошибку.
2. Закройте приложение обычным способом.
3. Пришлите `logs/errors.log` и последние строки `logs/app.log`. Если ошибка произошла раньше, приложите также соответствующий файл `.log.1`–`.log.5`.
4. Перед отправкой можно открыть журналы в Блокноте: они могут содержать локальные пути и идентификаторы диалогов, хотя содержимое переписки в них не сохраняется.

Обычный уровень — `INFO`. Для более подробной диагностики можно временно добавить в `.env`:

```dotenv
DEEPSEEK_LOG_LEVEL=DEBUG
```

После диагностики лучше вернуть `INFO`, иначе `app.log` будет заполняться быстрее.

Браузер откроет локальный адрес автоматически. Если порт `5000` занят, программа выберет следующий свободный порт. Остановка — `Ctrl+C` в консоли.

## Настройки запроса

- `model` — `deepseek-v4-flash` или `deepseek-v4-pro`;
- системный промпт;
- `temperature` и `top_p`;
- reasoning и `reasoning_effort` (`low`, `high`, `max`);
- необязательный `max_tokens`;
- до 16 стоп-последовательностей;
- обычный текст или JSON-объект;
- `logprobs` и необязательный `top_logprobs`.

В reasoning-режиме DeepSeek принимает `temperature` и `top_p`, но они не влияют на генерацию. Приложение всё равно сохраняет переданные значения. `seed`, `frequency_penalty` и `presence_penalty` не предлагаются: DeepSeek их не поддерживает либо больше не применяет.

## Как считаются токены

Счётчики берутся из фактического поля `usage` ответа DeepSeek, а не оцениваются по длине текста. **Контекст вызова** — это весь вход, который модель получила в конкретном запросе: системный промпт, выбранная версия истории и новое сообщение. **Σ диалога** — сумма `total_tokens` всех завершённых ответов; повторно отправленная история учитывается на каждом шаге. `Reasoning` показан как отдельная детализация `completion_tokens` и не прибавляется к общему итогу второй раз. Вызовы формирования handoff учитываются отдельно в `task_handoff_token_totals` и показываются в карточке контекста этапа. Для `deepseek-v4-flash` и `deepseek-v4-pro` используется документированное контекстное окно 1 000 000 токенов; полоса в шапке показывает `prompt_tokens` последнего завершённого вызова относительно этого окна. Это точное значение уже отправленного запроса, а не предварительная оценка ещё не отправленного текста.

## Сжатие истории — День 9

В правой панели **«Контекст»** выбирается режим конкретного диалога:

- **Полная история** — в каждый запрос передаются все успешные обмены текущего посещения этапа;
- **Summary + последние обмены** — передаётся накопительный summary и несжатый хвост истории.

Один обмен — это успешная пара `user + assistant`. Последние 5 обменов всегда передаются дословно. Когда перед ними накапливаются ещё 5 несжатых обменов, приложение вызывает `deepseek-v4-flash` с `reasoning=false`, создаёт новую версию summary и сворачивает в неё эту пятёрку. Поэтому несжатый хвост содержит от 5 до 9 обменов. На первом включении режима накопившаяся история обрабатывается последовательными группами по 5.

Summary добавляется к системному контексту основного запроса. Переключение обратно на полную историю не удаляет ни сообщения, ни созданные версии. В каждом ответе поле `technical.context_management` показывает, какой режим и какая версия summary реально использовались.

Файл `data/conversations/<id>.json` содержит:

- `messages` — полную исходную историю;
- `context_management` — режим диалога и ID действующего summary;
- `summaries` — неизменяемые версии, ID охваченных обменов и сообщений, модель и фактический `usage`;
- `summary_token_totals` возвращается API и показывает отдельную стоимость создания памяти.

Расход на обычные ответы и на суммаризацию показан раздельно. Для ручного сравнения задайте одинаковые вопросы в двух диалогах: в одном оставьте полную историю, во втором включите сжатие.

Стоимость намеренно не рассчитывается: приложение сравнивает только использование токенов и не привязано к тарифам.

Если реальный запрос превышает лимит контекста выбранной модели, API-вызов завершается ошибкой. Программа сохраняет неотправленное сообщение как неудачное, не добавляет его в будущий контекст и явно предлагает создать новый диалог или сократить историю.

## Стратегии контекста — День 10

В панели **«Контекст»** доступны четыре режима:

- **Полная история** — успешный активный путь внутри текущего `stage_run_id`;
- **Summary** — существующая накопительная суммаризация;
- **Sliding Window** — текущий запрос и последние N обменов, включая текущий незавершённый обмен;
- **Sticky Facts** — структурированные facts плюс такое же окно из N обменов.

Для Sliding Window и Sticky Facts значение N настраивается от 1 до 50, по умолчанию 5.

Sticky Facts используют универсальные группы ключей: `goal`, `context`, `entities`, `requirements`, `constraints`, `preferences`, `decisions`, `agreements`, `resources`, `environment`, `numbers`, `deadlines`, `definitions`, `output`, `open_questions`, `next_steps`, `risks`. Автоматическое обновление выполняет `deepseek-v4-flash` без reasoning и сохраняет отдельный фактический usage. Если извлечение не удалось, основной ответ продолжает использовать предыдущую память, а ошибка остаётся в `fact_revisions`.

Ветвление доступно поверх всех четырёх режимов. Кнопка слева под сообщением пользователя сразу создаёт новый вариант ответа DeepSeek; кнопка справа под ответом ассистента открывает пустое продолжение для нового пользовательского промпта. Исходная ветка имеет номер 1; следующие ветки в этой точке получают номера 2, 3 и далее. Удаление веток не предусмотрено. Старое сохранённое значение режима `branching` автоматически читается как `full`, при этом само дерево сообщений и все ветки сохраняются.

Все сообщения дерева хранятся один раз в `messages` и связаны через `parent_id`. Текущий лист записан в `context_management.active_leaf_id`; facts, их ревизии, summaries и ветки остаются в одном JSON-файле диалога. Старые линейные JSON-диалоги мигрируют при чтении без удаления исходных сообщений.
