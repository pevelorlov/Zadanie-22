# Карта проекта DeepSeek Agent

Этот файл предназначен для быстрого входа Codex в проект. Он описывает границы
модулей и направляет к нужным исходникам, но не заменяет проверку актуального
кода перед изменением.

## Быстрый маршрут чтения

1. Всегда учитывать правила из корневого `AGENTS.md`.
2. Для конкретной задачи выбрать область по таблице ниже.
3. Открыть только указанные файлы и связанные тесты в `test_app.py`.
4. Читать соседние модули только если меняется их контракт.

## Технологии и запуск

- Python 3.10+, Flask, OpenAI Python SDK с `base_url=https://api.deepseek.com`.
- Клиентская часть — обычные HTML, CSS и JavaScript без сборщика.
- Постоянное хранилище — локальные UTF-8 JSON-файлы и SQLite для Scheduler.
- Голос — локальный `whisper.cpp` server и FFmpeg.
- MCP — официальный Python SDK, Filesystem Server, четыре собственных сервера и
  готовые MediaWiki/World Bank Server по `stdio`.
- Обычный запуск Windows: `run.bat` -> `.venv\Scripts\python.exe main.py`.
- `main.py` находит свободный порт 5000–5100, открывает браузер и запускает
  Flask только на `127.0.0.1`.

## Основной поток сообщения

```text
static/app.js
  -> POST /api/conversations/<id>/messages
  -> app.py: определить активный профиль и проверить доступ к проекту
  -> app.py: проверить, что задача не приостановлена
  -> app.py: validate settings and save pending user message
  -> context_manager.py: update facts or summary when their mode is active
  -> context_manager.py: construct history for the current stage_run_id on the active tree path
  -> agent.py: add policy, profile, task state, active handoff, user/project memory, summary/facts, history and new message
  -> DeepSeekProvider.complete() или цикл complete_with_tools()
       → MediaWiki / World Bank / Open‑Meteo / Scheduler MCP → DeepSeek
       → при явном файловом экспорте: Open‑Meteo → DeepSeek → Filesystem write_file
  -> app.py: attach exact usage and settings snapshots, save assistant message
  -> storage.py: atomic JSON replacement
  -> static/app.js: render returned conversation
```

Сначала пользовательское сообщение сохраняется со статусом `pending`. При
успехе оно становится `completed`, рядом создаётся сообщение ассистента. При
ошибке пользовательское сообщение получает `failed` и впоследствии исключается
из контекста.

## Контекст и ветвление

В `context_management.mode` существует четыре режима:

- `full` — все успешные сообщения активного пути;
- `summary` — накопительный summary и последние дословные обмены;
- `sliding` — окно последних N обменов;
- `facts` — Sticky Facts и окно последних N обменов.

Ветвление — ортогональная возможность, а не значение режима. Все сообщения
хранятся один раз в `messages` и связаны через `parent_id`.
`context_management.active_leaf_id` выбирает текущий путь. После ветвления от
сообщения ассистента `pending_branch_from_id` задаёт точку для следующего
пользовательского сообщения. Удаление веток не реализовано.

Summary оставляет 5 последних успешных обменов дословно и сворачивает более
старые обмены пакетами по 5. Каждая версия сохраняется неизменяемой в
`summaries`; активная версия выбирается через `active_summary_id`.

Окна Sliding Window и Sticky Facts принимают значения 1–50, по умолчанию 5.
Автоматическое извлечение facts выполняется только в режиме `facts`. Ручной
fact имеет `locked=true` и не должен исчезать при автоматическом обновлении.

## Хранилище

```text
data/
├── presets.json
├── profiles.json
├── invariants.json
├── scheduler.sqlite3                  # задания, запуски и непрочитанные результаты
├── artifacts/<conversation id>/<artifact id>/<filename>
├── conversations/<32-символьный hex id>.json
├── projects/<32-символьный hex id>.json
└── memory/user_memory.json          # только источник однократной миграции старых данных
```

`data/` содержит пользовательские данные и игнорируется Git. Запись выполняется
во временный файл, затем атомарно заменяет основной через `os.replace`.
SQLite Scheduler использует WAL и короткие транзакции, чтобы HTTP-поток и
фоновый исполнитель безопасно читали и изменяли расписание одновременно.

## Scheduler и автоматизации

При обычном запуске `main.py` поднимает Scheduler MCP и поток `SchedulerService`.
MCP регистрирует 11 инструментов управления расписанием. Создание через чат
выполняется реальным `tools/call`; после ответа MCP приложение прикрепляет
активный профиль, проект и отдельный JSON-диалог автоматизации. В SQLite
сохраняются самодостаточный будущий промпт, настройки модели, тип расписания,
следующий запуск и allowlist MCP-серверов/инструментов.

Фоновый поток атомарно захватывает одно наступившее задание, запускает только
записанные зависимости и отправляет промпт через обычный endpoint сообщений с
профилем владельца. Ответ проходит стандартную политику, сохраняется в диалоге
и дублируется в истории запуска для агрегированной сводки. Результат становится
непрочитанным уведомлением интерфейса. Разовый запуск завершается, периодический
получает следующий будущий интервал.

На старте разовый запуск из прошлого получает `missed`; периодический перескакивает
к первому будущему времени без создания запусков за простой. Scheduler не
работает при остановленном Flask, не регистрируется в автозапуске Windows и не
посылает системные уведомления.

## Композиция MCP-инструментов

Для обычного сообщения `write_file` скрыт от модели, а Filesystem MCP может
оставаться остановленным. Если текст содержит явную положительную команду
сохранения файла/документа/отчёта, `app.py` лениво запускает Filesystem MCP,
получает актуальный `tools/list` и добавляет к инструментам DeepSeek только
`write_file`. Отрицательная команда вроде «не сохраняй» не включает экспорт.

DeepSeek сначала вызывает нужные инструменты Open‑Meteo, получает их
структурированный результат, выполняет смысловую обработку по исходному запросу
и передаёт полный Markdown в `write_file`. Перед настоящим `tools/call`
приложение отбрасывает предложенный каталог, нормализует имя и создаёт уникальный
путь `workspace/reports/<имя>-YYYY-MM-DD-HH-MM-SS.md`. Это сохраняет универсальную
роль модели: рекомендации не зашиты в погодные правила и могут зависеть от
вопроса пользователя. Успешный `write_file` фиксируется в `mcp_tool_calls` как
`file_export`; при блокировке поствалидацией созданный файл удаляется.

## Оркестрация MCP

`main.py` автоматически запускает установленные в `node_modules` ProfessionalWiki
MediaWiki MCP и World Bank MCP. Они имеют независимые менеджеры, процессы,
состояния и HTTP lifecycle-маршруты. Модели передаются шесть read-only
инструментов MediaWiki и девять read-only инструментов World Bank. Полный список
MediaWiki остаётся видимым пользователю, но операции записи, OAuth и управления
wiki не включаются в модельный allowlist.

Общий function-calling цикл сопоставляет уникальное имя инструмента с владельцем
и выполняет `tools/call` в соответствующей сессии. Системная инструкция требует
использовать результат первого сервера как фактический вход следующего, если
задача зависимая. Сервер-владелец, порядок, аргументы и ошибки сохраняются в
`mcp_tool_calls`.

Клиент создаёт случайный `mcp_activity_id` и во время HTTP-запроса опрашивает
`GET /api/mcp/activity/<id>`. Потокобезопасный реестр публикует только сервер,
имя, ограниченные аргументы и состояние вызова; содержимое файлов и секретные
поля маскируются. После ответа отдельный блок сообщения строится из постоянного
аудита, поэтому история вызовов не зависит от временного live-реестра.

Верхний уровень диалога schema version 3:

| Поле | Содержимое |
| --- | --- |
| `id`, `title`, `created_at`, `updated_at` | Идентификация и даты |
| `owner_profile_id` | Владелец диалога; у старых файлов — профиль по умолчанию |
| `messages` | Полная история дерева: `user`, `assistant`, технические `event` |
| `context_management` | Режим, размеры окон, активные summary/лист/точка ветки |
| `task_state` | Одна текущая задача: этап, шаг, ожидаемое действие, план, активность и журнал изменений |
| `task_handoffs` | Неизменяемые структурированные итоги завершённых посещений этапов |
| `artifacts` | Метаданные версий файлов: логический путь, размер, SHA-256, источник и результат проверки |
| `summaries` | Неизменяемые ревизии summary и их фактический usage |
| `facts` | Текущий набор структурированных фактов |
| `fact_revisions` | История автоматических обновлений и их usage/ошибки |

Вычисляемые представления (`visible_messages`, `branch_points`, агрегаты
токенов) добавляются `with_token_totals()` в API-ответ и не обязаны сохраняться
как источник истины.

`profiles.json` хранит активный профиль и независимые настройки персонализации,
manual/learned-память каждого профиля. Проект хранит `owner_profile_id` и
`participant_profile_ids`; участник видит весь проект и его диалоги. Диалог без
проекта видит только владелец. У пользовательского сообщения сохраняется
`author_profile_id`, а у ответа — неизменяемый снимок применённого профиля.

Импорт не перезаписывает существующий диалог: создаётся новый ID и добавляется
суффикс «— импорт». Экспорт имеет внешний формат `deepseek-agent-export` schema
version 1 и включает снимки использованных пресетов.

## Состояние задачи

`task_state` принадлежит диалогу и хранит одну текущую задачу: `description`,
`stage`, `current_step`, `expected_action`, `plan`, `activity`, `required_artifacts`, `updated_at` и
`transition_history`. `stage_run_id` отличает повторные посещения одного этапа,
а `active_handoff_ids` выбирает компактный контекст текущего этапа.
Этап — одно из `planning`, `execution`, `validation`, `done`; активность —
`active` или `paused`. Старые schema v3-диалоги получают безопасные значения
`planning`, `active` и пустой журнал при чтении.

Этап нельзя менять через обычный PATCH. `transition_mode` выбирает только способ
запуска разрешённых событий: `manual` показывает кнопки пользователю, а
`automatic` принимает рекомендацию последнего проверенного ответа и запускает
следующий этап служебным сообщением автопилота. Серверный автомат принимает
события `approve_plan`, `complete_execution`, `pass_validation`,
`return_to_planning`, `validation_failed`, `pause`, `resume`. Основной путь —
`planning → execution → validation → done`; разрешены откаты
`execution → planning` и `validation → execution`. Недопустимое событие даёт
HTTP 409 и не меняет состояние. Пауза не является этапом, блокирует переходы и
LLM-действия, а `resume` сохраняет прежние этап и шаг.

При `paused` сервер возвращает HTTP 409 до запуска LLM для отправки сообщения,
создания ветки и явного извлечения памяти из истории. Навигация, редактирование
состояния и возобновление остаются доступны. В основной запрос передаётся снимок
актуального состояния; тот же снимок сохраняется в `technical.task_state`.
Блок состояния ставится последним в системном промпте и явно объявляется
авторитетным: этап нельзя переопределять выводом из более старого контекста.
`GET .../task-state` и локальная команда `/state` формируют отчёт на сервере
без вызова LLM; локальная пара видна в истории, но не входит в будущий контекст
и не увеличивает счётчик запросов провайдера.

Для файлового результата валидатор планирования возвращает
`required_artifacts`. На выполнении модель использует именованный блок
`artifact path=index.html` с полным содержимым файла. Сервер безопасно пишет
его в `data/artifacts/`, регистрирует версию и SHA-256 и связывает запись с
сообщением и `stage_run_id`. Событие `complete_execution` не принимается при
отсутствии обязательного файла. Успешный ответ этапа `validation` повторно
читает файл и сверяет размер и хэш; `pass_validation` принимается только для
проверки текущего запуска этапа. После перехода в `done` сервер добавляет
детерминированное итоговое сообщение с `result_manifest`; API скачивания
проверяет доступ к исходному диалогу, а inline-просмотр получает sandbox CSP.
Для `pass_validation` переход сначала собирается на копии диалога: после
активации handoff модель вызывается с авторитетным состоянием `done` и точным
реестром файлов, а её ответ проходит обычный независимый контроллер. В ответ
детерминированно дописывается точный список артефактов и прикрепляется
`result_manifest`. Только затем копия атомарно сохраняется; ошибка финального
LLM-вызова оставляет исходную задачу на `validation`.

Основная модель получает этап, допустимые действия и все активные инварианты,
но возвращает обычный пользовательский текст без служебного JSON. После
генерации второй LLM-вызов возвращает проверяемый JSON с фактическим действием,
полным списком проверенных инвариантов и найденными нарушениями. Сервер сверяет
результат валидатора с таблицей допустимых действий этапа. Допустимость ответа
вычисляется сервером отдельно от `stage_complete`: разрешённый промежуточный
ответ сохраняется без перехода этапа. Заблокированная пара
получает `request_status=blocked`, не входит в будущий контекст и не показывает
опасный черновик. Снимок аудита находится в
`technical.policy_audit`; токены генерации и проверки учитываются раздельно и
суммарно. Кнопка повторной генерации создаёт альтернативный ответ к тому же
пользовательскому сообщению. Если новая проверка успешна, исходное сообщение и
новая ветка получают `completed` и входят в последующий контекст; при повторной
блокировке они остаются исключёнными.

При изменении этапа сервер до мутации состояния сворачивает успешные обмены
текущего `stage_run_id` в структурированный handoff: итог, утверждённый план,
решения, ограничения, критерии готовности, выполненную работу, результаты
проверки и открытые вопросы. Если извлечение завершается ошибкой, переход не
применяется. При отсутствии успешных обменов создаётся детерминированный handoff
из полей задачи без LLM-вызова. После перехода новый `stage_run_id` получает
базовую политику, профиль, память пользователя и проекта, инварианты, активную
цепочку handoff и только собственные успешные сообщения. История, старые summary
и facts сохраняются в JSON, но не отправляются в новый этап. Повторный вход в
`execution` после неуспешной валидации получает утверждённый план и свежие
замечания проверки. Ветвление от сообщений предыдущего этапа запрещено.

## Инварианты

`data/invariants.json` является отдельным источником истины. Наборы имеют scope
`user`, `project` или `task`, владельца области, список правил и переключатель
активности. Контекст собирается из read-only системной политики, активных
наборов профиля, проекта и конкретного диалога. Определения не записываются в
корень JSON диалога; у сообщений сохраняется только применённый снимок для
аудита. Владельцем проектных наборов управляет владелец проекта, пользовательские
принадлежат профилю, задачные доступны участнику диалога.

## Как локализовать типовую задачу

- Новый параметр модели: `agent.py` -> `app.py` -> элементы настроек в HTML/JS
  -> тесты -> README при пользовательском изменении.
- Новая стратегия памяти: `context_manager.py` -> JSON defaults/migration в
  `storage.py` -> API в `app.py` -> HTML/JS -> тесты -> документы.
- Изменение состояния задачи: `task_state.py` -> `storage.py` -> `app.py` ->
  `agent.py` -> HTML/JS -> тесты -> документы.
- Изменение сообщения или токенов: `agent.py`, поток `send_message()` в
  `app.py`, `renderMessageTokens()`/`renderTokenOverview()` в JS и тесты.
- Изменение JSON: сначала определить совместимость и миграцию, затем менять
  `storage.py`, нормализацию в `context_manager.py`, импорт/экспорт и тесты.
- Изменение веток: `context_manager.py` и branch routes в `app.py`, затем
  `renderBranchSwitch()`/`createBranch()` в JS и тесты branching.
- Изменение голоса: `voice.py`, voice routes, UI записи, setup-скрипты и тестовый
  fake voice service.
- Изменение расписания: `scheduler.py` -> Scheduler MCP -> `app.py` -> окно
  расписания в HTML/JS -> `test_scheduler.py` -> документы.
- Изменение композиции MCP: `app.py` -> `agent.py` (общий function-calling цикл)
  -> `mcp_manager.py` -> `test_app.py`/`test_mcp_servers.py` -> документы.
- Изменение только внешнего вида: `templates/index.html` и `static/style.css`;
  JS открывать только при изменении поведения или DOM-контракта.

## Проверка

Базовый набор команд указан в `AGENTS.md`. Тесты не совершают реальных вызовов
DeepSeek и не расходуют API-средства. Для изменения интерфейса требуется также
целевая браузерная проверка без отправки реального сообщения модели.
